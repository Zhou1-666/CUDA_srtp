## 1. 项目真实定位

本仓库不是完整 CFD 求解器，而是面向 CFD/PDE 应用的并行带状线性方程求解器：

- 上游：PaScaL_TDMA 2.1，多 GPU 三对角求解；
- 已实现扩展：CUDA Fortran 五对角分布式求解；
- 已完成理论原型：半带宽 `m=1..6` 的一般带状缩约结构和递推验证；
- 已有实验：RTX 4060 Laptop + WSL2 单卡多 rank 基准；
- 尚缺关键证据：真实多 GPU 节点上的正确性、通信收益和强/弱扩展。

因此 SRTP 和论文应聚焦：**分布式五对角/一般带状求解器的正确实现、通信结构裁剪与多 GPU 可扩展性**。把项目包装成“完整 GPU CFD 软件”会造成范围和证据不匹配。

## 3. 五对角执行链路

多 rank 路径按六段执行：

1. `tdma_modified_penta`：每条线本地消元，产生 4 条接口方程；
2. `pascalpack`：按目标 rank 打包当前每线 28 个 double；
3. 第一次 `pascal_a2av`：交换缩约系数；
4. `pascalunpack_penta` + `tdma_many_cuda`：组装并求解 `4P × 4P` 缩约系统；
5. 第二次 `pascal_a2av`：把 4 个接口解回传原 rank；
6. `pascal_update_penta`：回代重建全部内部未知量。

当前 28 个 double 来自 4 条接口方程 × 每方程 7 槽，恒等对角已省略。理论与脚本表明还能省去 6 个结构恒零槽，目标应为 **28→22（约减少 21% 前向缩约数据）**，不是 28→18。

## 5. 关键问题与优先级

### P0：基线发布阻断

1. **未初始化 MPI 请求被等待。** 两个 Fortran 模块都先调用阻塞式 `MPI_ALLTOALLV`，随后对从未赋值的 `requestA/requestB` 调用 `MPI_WAITALL`。这是未定义行为；应删除无效 wait，或真正改成非阻塞通信并只等待已创建请求。
2. **许可证与来源未固化。** README 写 `To be defined`，仓库无明确 LICENSE；上游论文说明原项目为 MIT。需要识别哪些文件来自上游、哪些为本项目新增，并补许可和引用。
3. **当前目录没有 Git 仓库。** 无法用提交哈希冻结实验和论文证据；建议在确认目录边界后初始化 Git 或迁入正式仓库。

### P1：正确性与可维护性

1. `Nrow>=5` 只是注释约束，API 没有运行时检查；
2. 未检查 `Nsys>0`、`nprocs>0`、线程块范围以及 `Nsys<nprocs` 的空分区；
3. 普通求解路径缺少 CUDA kernel launch/error 检查；
4. `pascal_setcudathread` 是空实现，公开 API 会造成误导；
5. 求解原位覆盖系数和 RHS，但 README 没有完整说明五对角 API 与所有权；
6. 二进制、`.o`、`.mod`、静态库、图片和历史结果与源码混放，且没有 `.gitignore`。

### P1：大规模索引风险

当前维度、MPI count/disp 和数组边界主要使用默认 32 位 `integer`。风险集中在：

- `32*nprocs`、`4*nprocs`；
- `Nsys*28`、`tmp_N*32`、缓冲区累计偏移；
- 超大 CFD 网格中的线数×线长和 CUDA 启动规模。

不要全局改成 64 位。应先为上述乘法与累计偏移建立上界检查：设置/分配阶段需要时局部用 64 位计算并检查 MPI `INTEGER` count 限制；热内核的逐元素索引只有可能跨越 32 位地址范围时才引入 32/64 位双路径或显式拒绝超限输入。

### P2：性能机会

1. host staging 路径每次通信都 `allocate/deallocate(hA,hB)`，应改为 plan 生命周期内复用，必要时用 pinned host memory；
2. 落地 28→22 结构零槽裁剪，并做同一硬件、同一问题的消融；
3. 在支持的集群上比较 host staging 与 CUDA-aware MPI；
4. 对 S1/S6、pack/unpack 做 Nsight 分析，避免先凭直觉重写；
5. 后续再评估非阻塞通信与计算重叠，不能与 28→22 同时修改。

## 6. 现有性能结果应如何解释

现有基准在单块 RTX 4060 Laptop 8GB、WSL2、OpenMPI host staging 上运行。实验组相对参考组约快 `2.6–4.7×`，相对单进程串行组约快 `3.4–3.7×`，但 `np=1→2/4` 是负扩展。

这些数据可用于：

- 验证 benchmark 流程、误差与计时字段；
- 说明当前实现相对本仓库参考实现的性能潜力；
- 发现单卡多进程的显存与调度限制。

这些数据不能用于：

- 声称多 GPU 强/弱扩展；
- 证明 CUDA-aware MPI 或 28→22 已带来收益；
- 与不同硬件、不同精度或不同终止准则的外部结果直接比较。

## 8. 论文最合理的研究主线

建议题目方向：

> 面向大规模 CFD 的通信裁剪多 GPU 五对角求解器：缩约结构、实现与性能评估

可形成的论证链：

1. 从 PaScaL 三对角方法推广到五对角，推导 `4P × 4P` 缩约系统；
2. 进一步给出一般半带宽 `m` 的接口规模、带宽和槽位公式；
3. 证明并验证结构零槽数量 `3m(m-1)`，通信下界为 `5m²+m`；
4. 在五对角实现中落地 28→22；
5. 用真实多 GPU 数据报告正确性、通信时间、端到端时间和可扩展性。

“首次”“最优”或与所有同类方法相比的结论，必须等系统文献检索与实验完成后再决定。
