# 单任务完成、复验与下一任务交接协议

> 目的：让每个 GPT/Codex 任务成为一个独立、可复验、可交接的开发闭环。

## 1. 基本规则

- 一次只领取 `task-queue.md` 中一个可执行任务；
- 开始前冻结目标、允许修改文件、禁止修改内容、验证命令和停止条件；
- 完成当前任务后只推荐下一任务，不在同一上下文顺手实施；
- 自动检查通过不代表目标环境通过；缺少 NVHPC/MPI/GPU/HPC 证据时必须明确保留状态；
- 不能因为模型认为代码“看起来正确”就把任务标为 `done`。

## 2. 完成状态判定

| 状态 | 使用条件 |
| --- | --- |
| `done` | 任务合同中的代码、自动检查、目标环境验证和记录全部完成 |
| `review` | 实现与本地检查完成，等待独立审查或目标环境复验 |
| `blocked` | 明确缺少环境、材料、权限或人工决策，无法继续验收 |
| `in-progress` | 仍有可在当前环境继续完成的工作 |

例如：删除无效 `MPI_WAITALL` 后五项 Node 检查通过，但尚未在 NVHPC + MPI 环境构建，TASK-001 不能标记 `done`。

## 3. 每次交接必须包含

```text
任务：TASK-XXX / 名称
状态：done | review | blocked | in-progress

完成结果：
- 实际实现了什么；
- 明确没有改变什么。

修改文件：
- 文件及职责。

已执行验证：
- 完整命令；
- 退出码、误差、用例数或构建结果；
- 证据保存位置。

用户如何复验：
1. 前置环境；
2. 可复制命令；
3. 预期输出/阈值；
4. 失败时保存哪些日志。

未覆盖范围：
- 当前证据不能证明什么。

下一任务：
- 唯一推荐的 TASK；
- 依赖与停止条件；
- 推荐模型和推理强度。
```

## 4. 验证内容放在哪里

| 内容 | 存放位置 |
| --- | --- |
| 稳定、长期复用的命令 | `程序正确性与性能运行手册.md`、`wiki/testing/test-matrix.md` |
| 每个任务的目标和状态 | `meta/task-queue.md` |
| 单次运行结果、失败日志摘要 | `knowledge/outputs/queries/` 或 `wiki/experiments/` |
| 设计取舍变化 | `wiki/decisions/ADR-*` |
| 可写入论文的结论 | `wiki/paper/claim-evidence-matrix.md` |
| 给用户的即时交接 | 当前任务最终回复 |

验证命令应同时写清工作目录、依赖、输入规模、预期退出码和数值阈值。性能任务还必须记录硬件、软件版本、rank/GPU 映射和重复次数。

## 5. 下一任务选择规则

1. 优先当前阶段尚未完成的 P0；
2. 只选择依赖已经满足的任务；
3. 如果最高优先级任务被环境阻塞，先推荐解除阻塞所需的最小动作；
4. 不为了“保持忙碌”提前进入会污染当前 Gate 的性能优化；
5. 推荐时给出模型与推理强度，但最终验收依赖测试证据。

## 6. 何时编译成 Skill

当前先由 `AGENTS.md` 和本协议执行，不立即建立正式 Skill。满足以下条件后，再把稳定部分提炼为 `pascal-sprint-executor`：

- P0 修复已在目标 NVHPC + MPI 环境复现；
- 统一检查入口经过至少两个真实任务使用；
- 至少完成一次 28→22 的实现—验证—实验记录闭环；
- 任务类型到验证命令的映射已经稳定。

未来 Skill 只自动化“选择一个任务—执行—验证—记录—推荐下一任务”，不能自动改变论文主线、验收阈值、许可证或发布状态。
