# 单任务完成、复验与下一任务交接协议

> 目的：让每个 GPT/Codex 任务成为一个独立、可复验、可交接的开发闭环。

## 1. 基本规则

- 一次只领取 `task-queue.md` 中一个可执行任务；
- 开始前冻结目标、允许修改文件、禁止修改内容、验证命令和停止条件；
- 完成当前任务后只推荐下一任务，不在同一上下文顺手实施；
- 自动检查通过不代表目标环境通过；缺少 NVHPC/MPI/GPU/HPC 证据时必须明确保留状态；
- 不能因为模型认为代码“看起来正确”就把任务标为 `done`。
- 核心源码候选按 [[../wiki/testing/source-change-validation-sop]] 附逐门禁回执、实际构建源码/测试/flags 指纹、用例数与完整日志。未运行不得填 PASS；范围豁免须明确批准。文档交付与 solver 目标回归分别验收。
- 每次交接必须核对 [[task-blocker-register]]，有变化才更新对应条目；无变化在回执注明。状态不是说明，台账中的“当前缺口、责任方、解除证据、最小动作”才是未完成任务的验收依据。

## 2. 完成状态判定

| 状态 | 使用条件 |
| --- | --- |
| `done` | 任务合同已按证据关闭：正常交付完成适用验收；实验可按预注册采用门关闭为不采用；未完成门禁的撤回须有用户明确批准的停止规则或关闭决定。必须另记处置及未覆盖项 |
| `review` | 实现与本地检查完成，等待独立审查或目标环境复验 |
| `blocked` | 明确缺少环境、材料、权限或人工决策，无法继续验收 |
| `in-progress` | 仍有可在当前环境继续完成的工作 |

例如：删除无效 `MPI_WAITALL` 后五项 Node 检查通过，但尚未在 NVHPC + MPI 环境构建，TASK-001 不能标记 `done`。

### 关闭处置与门禁分别记录

- `done` 必须记录关闭类型（正常交付／不采用／撤回）、依据、关闭人或决定来源、日期和回执。源码候选另记采用结论；任务关闭不等于候选获准合并。
- 正常采用候选仍须满足适用 SOP；负结果不能伪装为加速，环境限制不能自动触发 done。只有按已批准的停止规则完成撤回处置，才允许任务关闭而保留未运行门禁。
- FAIL、NOT-RUN、UNKNOWN 原样保留，写明是 solver、工具、环境或证据缺口；不得随任务关闭改为 PASS。TASK-025 的负结果记作不采用，TASK-007 按批准规则撤回，不重开历史合同。
- 所有 done 任务保留最短关闭快照，即使从未 blocked；历史缺项只凭原回执补录，注明补录日期，不编造曾有阻塞或原关闭日期。

## 3. 每次交接必须包含

```text
任务：TASK-XXX / 名称
状态：done | review | blocked | in-progress
关闭处置（仅 done）：正常交付 | 不采用 | 撤回；决定来源、日期、证据与保留的未运行门禁

完成结果：
- 实际实现了什么；
- 明确没有改变什么。

修改文件：
- 文件及职责。

已执行验证：
- 完整命令；
- 退出码、误差、用例数或构建结果；
- 证据保存位置。

用户如何复验：
1. 前置环境；
2. 可复制命令；
3. 预期输出/阈值；
4. 失败时保存哪些日志。

未覆盖范围：
- 当前证据不能证明什么。

缺口台账：
- 若非 done：更新的 `task-blocker-register.md` 条目及仍缺的具体证据；
- 若 done：已解除快照、关闭人和证据路径。

下一任务：
- 唯一推荐的 TASK；
- 依赖与停止条件；
- 起步模型与推理强度、必要时的审阅档位、升档触发条件；不得机械沿用上一任务的XHigh。
```

## 4. 验证内容放在哪里

| 内容 | 存放位置 |
| --- | --- |
| 稳定、长期复用的命令 | `程序正确性与性能运行手册.md`、`wiki/testing/test-matrix.md` |
| 每个任务的目标和状态 | `meta/task-queue.md` |
| 非 done 任务的具体缺口、责任方和解除动作 | `meta/task-blocker-register.md` |
| 单次运行、失败与逐次排障 | 对应 `knowledge/outputs/validation/<任务或候选>/` 回执；运行原件放其 `raw/`。问答放 outputs/queries，可复用实验结论再编译到 Wiki |
| 设计取舍变化 | `wiki/decisions/ADR-*` |
| 可写入论文的结论 | `wiki/paper/claim-evidence-matrix.md` |
| 给用户的即时交接 | 当前任务最终回复 |
| 已完成里程碑 | `meta/compile-log.md` 中的日期、结果和回执指针；不复制逐次命令或排程全文 |

验证命令应同时写清工作目录、依赖、输入规模、预期退出码和数值阈值。性能任务还必须记录硬件、软件版本、rank/GPU 映射和重复次数。

## 5. 下一任务选择规则

1. 优先当前阶段尚未完成的 P0；
2. 只选择依赖已经满足的任务；
3. 如果最高优先级任务被环境阻塞，先推荐解除阻塞所需的最小动作；
4. 不为了“保持忙碌”提前进入会污染当前 Gate 的性能优化；
5. 每项任务在task-queue模型列附完整模型名、起步档位和必要的分阶段建议；后续交接引用该列，不把历史回执的模型配置当默认。
6. 按2026-09-09用户要求控制用量：例行文档/归档用Low或Medium，明确合同的常规工程工作用Medium，复杂合同/跨文件审阅用High。XHigh须对应High仍难解决的具体证明、并发、等价或证据冲突，完成专项后回到起步档位。
7. 选档不改变任务状态、排程、数值门、独立审查/人工确认和执行授权；不得以省用量省略必需验证。模型/档位为工程推荐，实际运行设置须在应用中选择。

“唯一下一任务”是当时依赖与授权条件下的推荐，不是永久排程。用户明确决定或经用户批准的高层计划可以覆盖推荐；由维护者依据授权在 queue 记录一条“排程覆盖”，无需用户亲自编辑文件。最小字段为：决策者、日期、原顺序、新顺序、生效条件/范围、依据链接。旧推荐保留为带日期的历史，之后以该决定维护当前顺序。

覆盖未来顺序不等于中断当前任务，不自动解除依赖或验收 Gate，也不新增 SSH、GPU 提交、Git 合并或发布授权。没有明确决策依据时，不把推测当作排程覆盖。

## 6. 知识维护 Skill（按需）

2026-08-26 用户批准建立轻量 `penta-knowledge-maintainer`，将现有来源登记、实验归档和任务交接流程提供为按需入口；不建立自动执行软件任务的 `pascal-sprint-executor`。版本和验证见 [[../outputs/validation/KB-SKILL-001-20260826-penta-knowledge-maintainer/README]]。

`AGENTS.md` 与现有协议仍保留项目规则，skill 只路由最小材料。调用它不授权代码优化、集群作业、阈值修改、Git 推送、许可变更或公开发布。用户明确选中的当前任务不能被默认排程静默替换。

稀缺远端 allocation 的待提交 batch 另按 [cluster-submit-preflight](../../../skills/cluster-submit-preflight/SKILL.md) 先形成逐命令 A/B 分类：登录节点可安全只读复现的 A 类必须对冻结真实产物留证；GPU、MPI、solver 等 B 类保持 `NOT-RUN/UNKNOWN` 至目标运行。该 skill 的文档或 lint 通过不替代任务合同中的目标环境 Gate。
