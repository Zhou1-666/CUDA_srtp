# 五对角源码变更验证 SOP

本 SOP 把“改了代码”与“可以接受这个版本”分开：每个准备验收的核心源码候选版本，都要有数学、实际 GPU 程序和分布式运行证据。不是每保存一行就申请一次集群，也不是用一次测试证明所有输入永远正确。

流程要求来自 2026-08-26 用户请求和项目规则；SRC-003P/004 是已有实现/理论背景，SRC-024 是既有制造解回归依据，不是本 SOP 已在新源码上全程通过的证据。[本次文档交付回执](../../outputs/validation/KB-SOP-001-20260826-source-change-validation/README.md)与未来源码验收回执必须分开。

## 1. 适用范围与执行时点

- 核心变更：消元/缩约/回代、槽位布局、kernel、索引、plan/内存生命周期、MPI、同步/stream、错误路径，以及影响这些行为的构建或运行配置。
- 诊断变更：profiled 路径或计时/CSV 改动，既要验证诊断结果，也要对照普通路径的数值与扰动；触及求解器时按核心变更验收。
- 文档变更：运行知识 lint、链接和事实核对；不要求为纯文字改动重新申请 GPU。仅修改测试工具时，验证工具本身及受影响的目标用例；不得把工具 PASS 当成 solver PASS。
- 编辑迭代时先做快速检查；准备接受、交接为 `done` 或采用优化时，执行完整适用门禁。局部预检不等于最终验收。
- 验证绑定实际源码指纹。验证后再改源码/flags/受影响配置，原结果不得直接覆盖新版本；重新执行受影响门禁，复用不受影响证据必须写明依赖分析并经审阅认可。
- 核心候选版本默认包含真实单 GPU、单节点多 GPU和跨节点正确性，不以单 GPU 多 rank 替代。缩小支持范围/豁免门禁须用户明确批准并记录，执行者不能自行填“不适用”。

该 SOP 是执行与验收规范，不是已安装的自动 CI；不授予 SSH、GPU 资源申请、Git 合并/推送或发布权限。不重开历史已关闭任务，但历史二进制和回执不能替新候选验收。

## 2. 修改前：冻结合同

1. 读取当前任务、阻塞台账、[[../../meta/change-impact-map]] 和本页；只处理一个目标，算法、重构、性能优化不混做。
2. 登记基线和候选的 commit、未提交 diff、受影响源码/测试/Makefile 的 SHA256；不能只记 commit 而漏掉脏工作区。远端实际构建输入也要核对 SHA。
3. 列出允许修改文件、数学不变量、支持范围、用例矩阵、误差阈值、超时和性能采用门槛。修复先准备可复现失败用例；新行为补独立真值用例。
4. 记录硬件/GPU UUID、节点和互联、驱动/CUDA、NVHPC/MPI、编译 flags、FP64、host/device 后端、rank→hostname→GPU UUID、输入规模和种子。影响全局问题、后端选择和集体调用顺序的参数/环境须在各 rank 一致；rank 号、本地分区和 GPU 绑定则按合同各自核对。
5. 在已授权的独立候选目录中干净构建；不得清理其他任务正在使用的目录，不得用旧 `.o/.mod/a.out` 充当新构建。基线与候选分目录，不并发复用同一构建树。

停止条件：数值/内存/通信异常、错误拒绝语义改变、超时/死锁、源码指纹不符、缺少必需权限或环境时，停止当前验收链并留存证据；先定位原因，不用调宽阈值、删用例或换数据掩盖失败。

## 3. 逐级门禁

编号沿用 [[test-matrix]] 的 L0–L7，执行顺序如下；下表是新候选验收规则，旧任务的“最低测试”只作为局部检查参考。

| 顺序 / 门禁 | 必做内容 | 通过证据 |
| --- | --- | --- |
| 1 / L0 文档与静态 | 变更范围、调用点、接口/所有权、索引/描述符、知识 lint；算法改动补推导到代码的对应审查 | diff、指纹、检查输出和不变量清单 |
| 2 / L1 独立数学 | 当前八项数学脚本及容量自检；28/22 逐槽等价；算法改动增加独立参考/故障复现 | 每脚本用例数、误差、失败数；不是只看总 PASS |
| 3 / L2 目标构建 | 目标 NVHPC+MPI 环境分别干净 debug/release 构建相关库、示例、验证器和 benchmark；记录实际 flags | 新建对象/库/可执行文件、完整 build log、退出码 |
| 4 / L3 单 GPU | 真实 P=1，28/22，普通/profiled 实际涉及路径；独立真值、边界、稳定性和非法 API | 每用例数值与预期成功/拒绝；debug/release 均覆盖正确性 |
| 5 / L4 单节点多 GPU | 至少 2 张不同 UUID GPU、一 rank/卡；28/22，均匀/不均匀分配、小/常规规模；涉及多 peer/分区时再测 P=4 | 绑定收据、逐 rank 日志、全局误差、无死锁/错位 |
| 6 / L6 内存与生命周期 | 28/22 各 100 次 create–solve–clean；Compute Sanitizer memcheck/initcheck 覆盖每 rank；stream/共享内存/同步改动加适用 racecheck/synccheck 与故障用例 | 预期每个进程都有结果、0 非预期错误、无泄漏/悬挂；不把 GPU sanitizer 当作 MPI 竞态证明 |
| 7 / L7 跨节点正确性 | 至少 2 节点、2 GPU，一 rank/卡，28/22、制造解、均匀/不均匀分解、超时和退出检查 | 不同 hostname 与 UUID、实际网络/backend、每例误差及全部 rank 完成 |
| 8 / 集成回归 | 用候选库重新链接 TASK-010 制造解 demo，跑冻结 32 例与独立审计；不能直接复跑旧归档可执行文件 | 完整用例笛卡尔积、残差与收敛阶、库与 harness 指纹 |
| 9 / L5 与 L7 性能 | 正确性通过后做基线/候选配对计时；优化按预注册门槛判定；支持/宣称 1/2/4/8 GPU 扩展时复跑相应强弱扩展矩阵 | 原始绝对时间、误差、重复统计、拓扑与范围限定 |
| 10 / 审查与归档 | 算法/数值/通信变更由非原实现者审查；核对门禁、原始日志和指纹，更新任务及证据 | 所有必需项 PASS，或明确非 done 的缺口清单 |

L4/L7 的 host-staging 是基本路径；若支持/改动 CUDA-aware device 路径，须在对应拓扑先过最小 device MPI smoke，再跑同类回归。环境不支持时明确排除该环境下的 device 主张；不能把 host 结果填作 device 通过。新增支持范围须先修改合同，不能事后由测试结果倒推范围。

完整 1/2/4/8 强弱扩展不需要每次编辑都跑；最终组合验收/发布及相关扩展性主张须按 TASK-031 和 [[../performance/benchmark-protocol]] 补齐。只过双卡跨节点小例不能证明 8 卡扩展性能。

## 4. 数学正确性怎么判

### 独立性与指标

- 小系统使用独立稠密直解对照，制造解独立构造 `b=A*x_true`；不能调用待测缩约过程生成“真值”。28 槽与 22 槽相同只证明互相一致，不能排除共同错误。
- Node 模型验证公式，不直接验证编译后的 CUDA Fortran。实际 GPU 解也必须对照独立真值，并检查分区交界处、首尾行和所有系统。
- 求解器会原位覆盖 RHS/部分系数；保留原始 `A,b` 再计算残差。每次重复调用按合同重置输入，不能用已消元数组作为新问题。
- 同时报前向解误差与残差/归一化后向误差。每项注明范数与分母，例如 `||x-x_true||inf`、`||Ax-b||inf/(||A||inf*||x||inf+||b||inf)`；分母为零的规则必须预先定义，不隐式产生 NaN。
- 不将不同归一化口径混用同一阈值；沿用各已冻结验证器的定义。近奇异矩阵残差小不保证前向误差小；当前算法无主元交换，不承诺任意非奇异系统都可稳定求解。

### 已冻结数值合同（不得为提速放宽）

| 用例/指标 | 验收条件 |
| --- | --- |
| `penta_indep_check.js` 当前数学模型 | 与稠密直解最大差 ≤ `1e-10`；相对残差 ≤ `1e-11`；所有配置无失败、无非有限指标 |
| 常规制造解、对角占优/弱占优/跨尺度稳定性 | 沿用对应验证器口径；常规前向/归一化后向误差 ≤ `1e-10` |
| 受控近奇异族 | 后向误差 ≤ `1e-10`、前向误差 ≤ `1e-5`，两者必须同时报告，不推广到任意近奇异输入 |
| 28/22 交叉误差 | 不高于相同 baseline 容差，同时两者各自通过独立真值 |
| 主元保护 | 除法前 `abs(pivot) > 64*epsilon(FP64)*row_scale`；零/近零主元以 `numerical pivot breakdown` 和错误码 `4` 拒绝，不能以 NaN/Inf 代替 |
| TASK-010 制造解 | scaled residual ≤ `1e-10`；64→128、128→256 的 L2/Linf 收敛阶均 ≥ `3.8` |

输入矩阵至少包含：合法本地 `Nrow=5/6/8/16` 与代表性大尺寸、合法 `Nsys=1`（仅 P=1）、`Nsys=P/P+1`、非 P 整除及大规模；exact1、非平凡制造解、随机对角占优及稳定性矩阵族；28/22 两布局。具体全局尺寸由分解规则换算，不能误将全局 Nrow 当成本地 Nrow。

保留所有非法 API 例：`Nrow<5`、`Nsys<=0`、`Nsys<P`、非法线程数、communicator/rank/size 不一致、生命周期误用，以及 32 位索引/MPI count/displacement/工作区超限。超限例只做 setup-only 提前拒绝，不能先尝试巨大分配。预期失败须匹配对应诊断、非零退出和不死锁；数值失败另核对码 4，MPI launcher 的外层返回码不能代替内部错误证据。

TASK-010 完整矩阵：FP64，`Nx=16,Ny=8`，`lambda=0/1 × np=1/2 × slots=28/22 × Nz=32/64/128/256`，共 32 例。检查原始表头、每例恰一行、有限非负指标、无重复/漏例；运行器 PASS 不能替代独立审计。归档参考为 SRC-024，重新验收必须使用候选库。

## 5. 当前入口与使用限制

### Windows 本地快速检查（不申请 GPU）

从仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\CUDA_coding\scripts\check_all.ps1
```

当前入口包含知识 lint、八项数学检查（五对角独立/28/22/索引/稳定性、七对角、一般 m 结构/递推）和容量模型自检。预期退出 0、`Math check summary: Scripts=8, Failures=0`、`All available local checks: PASS`，还必须核对每个子脚本输出。一般 m/七对角是既有模型回归，不授权修改冻结三对角源码。

已知限制：`check_math.ps1` 只汇总退出码；当前 `penta_indep_check.js` 数值失败分支只打印失败而未设置非零退出码。验收必须额外检查失败行/配置数/数值有限性及阈值；这一入口尚不是可无人值守的完整正确性门禁。修复运行器应另立工具改动，不在测试时偷偷修改判定器。

### Linux / NVHPC / MPI 目标入口

下列为源码根 `CUDA_coding/CUDA_code/源代码` 下的真实脚本，不是一条能在所有集群直接运行的通用命令。执行前检查本版本参数、目标目录、MPI launcher 和已授权的 GPU 绑定；有些脚本自行 `make veryclean`，只能在独立候选构建目录顺序运行。

| 入口 | 当前覆盖与人工验收补充 |
| --- | --- |
| `verify/run_penta_api_validation.sh` | 当前 18 例，期望 `cases=18 failures=0`；自身不 clean，先确保候选干净构建；预期失败须检查具体诊断 |
| `verify/run_task_006_28_22.sh` | API + 20 个 profiled 小例 + 2 个普通示例，含 P=1/2/4、最小 Nrow 和不均匀分区；不能从 `solver finished` 推导独立正确性，普通路径仍需制造解数值回归 |
| `verify/run_task_015_stability.sh` | P=1/2，六类正反用例，共 12 例；失败分支还要核对主元保护/错误码证据，不只看守卫文本 |
| `verify/run_task_016_lifecycle.sh` | 默认 28/22 各 100 次；含双 rank memcheck/initcheck，默认共 6 例；需每 rank 的 sanitizer 结果和真实 GPU 映射 |
| `verify/run_task_007_profile_timing.sh` | profile-only 阶段字段/计时诊断；与普通路径对照，不能替代无 profiler 的完整性能基线 |
| TASK-010 归档 `source/verify/run_task_010_manufactured.sh` | 主源码树尚无统一集成入口；在独立候选树准备已审查 harness 并链接候选库，再执行 32 例。不得在原始归档上构建/覆盖 |

上述多项脚本写死 OpenMPI `--mca` 参数或 `mpirun`，换 MPI/Slurm 环境不能盲跑；有的依赖 `FC=mpifort` 和 `timeout`。现有脚本不自动证明 GPU UUID 唯一、不自动覆盖跨节点全部组合，也不都严格检查 CSV 表头/非有限值。执行合同须补绑定、环境和独立日志审计；必要的运行器修改单独审阅。

`verify/run_task_014_baseline.sh` 当前仍按旧首字段 `exp/ref/serial` 解析，而新 benchmark 是 `penta,exp,...`。它保留为历史入口，在版本适配与测试完成前不能作为当前候选验收命令。原始回执保持不变。

目标环境命令必须由执行者在回执中展开成真实绝对路径、launcher 参数、编译 flags、输出目录和资源映射；尚未核验的占位命令不计入“可复验”。重定向/`tee` 时保留程序真实退出码，避免管道最后一段掩盖失败。

## 6. 性能与正确性分开验收

1. 先过数值、安全和通信门禁。优化“更快但结果/错误语义改变”即失败；正确但未达到采用门槛，可关闭为否定实验，不能宣布优化成功。
2. 同硬件/拓扑/输入/精度/flags，基线和候选配对。默认沿用当前正式实验口径：2 次独立预热启动、至少 5 次正式独立启动；每次迭代数按任务冻结合同（TASK-007 为 10）。不同口径另记，不静默合并会话。
3. 冻结计时边界：solver-only 或端到端、分配/预处理/同步是否计入、首次调用或稳态。普通 solver 的外层计时应覆盖实际 GPU 完成，并取 rank 最大墙钟；不能只量异步提交时间。
4. Nsight/profiled 数据用于定位阶段；额外同步可能扰动执行，须对照普通路径。各阶段 rank MAX 可能来自不同 rank，不能机械相加当成真实关键路径或总墙钟。不能用屏幕 `avg_time(s)` 代替已定义的并行总时间。
5. 保存每次原始 CSV 和误差，报告中位数、IQR/MAD及波动；预注册异常处理，失败/超时/非有限样本不得静默剔除。工具崩溃与 solver 崩溃分开记录。
6. 数值回归通过只支持正确性范围；多卡慢不自动说明程序算错，性能变好也不证明算法正确。扩展性必须在真实拓扑和固定强/弱扩展口径下判断。

## 7. 回执模板与完成判定

每个候选保存到 `knowledge/outputs/validation/<任务>-<日期>-<环境>/`，至少包含源码/构建指纹、环境/绑定、命令、完整 stdout/stderr、原始 CSV、审计输出和以下清单：

```text
任务 / 候选版本 / 基线版本：
单一目标、修改文件、禁止改变项：
实际构建源码 SHA256 / diff / flags / harness SHA：
环境、拓扑、backend、rank-hostname-GPU UUID：
L0 / L1 / L2 debug+release / L3 / L4 / L6 / L7 / 集成 / 性能 / 审查：
  状态 = PASS | FAIL | NOT-RUN | N/A（须批准及原因）
  命令与工作目录、输入、期望用例数、实际用例数：
  退出码、误差/阈值、预期失败数、日志与 CSV 路径：
验证后源码是否变化 / 复用证据的依赖审查：
未覆盖范围、责任方、解除所需证据与最小动作：
结论 = done | review | blocked | in-progress：
审阅人 / 采用或否定理由 / 核对日期：
人工复验命令、预期输出、失败时保存的材料：
唯一下一任务、依赖、模型/推理强度（只推荐不启动）：
```

缺单 GPU/真实多 GPU/跨节点/独立真值等必需证据，就写“本地预检通过，完整验收未完成”，不能写“数学正确性已保证”。不能把 NOT-RUN 当 PASS，也不能把许可/权限问题归咎于算法。

执行者更新 [[../../meta/task-blocker-register]] 中具体缺口、类别、责任方、解除证据、最小动作和核对日期；通过后保留已解除快照，并按 [[../../meta/task-handoff-protocol]] 同步任务与适用实验/论文证据。只有所承诺范围内的必需门禁和审查全部完成，才可标记 `done`。
