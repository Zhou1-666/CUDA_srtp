## 五、研究过程

模板要求写实际做过的经过、步骤、方法和关键技术，而不是立项时的设想。下面按真实工作顺序来写。

### 5.1 研究经过、步骤

立项时，申报书里写的是 GPU 加速不可压缩 CFD 软件，里面还包括 FFT 降维、批量几何多重网格、全显存驻留和标准流场算例。真正动手以后我们发现，仓库里已经比较完整的，其实是一套 CUDA Fortran + MPI 的分布式带状线性求解器：上游是公开的 PaScaL_TDMA 三对角方法，本项目在此基础上做五对角扩展。完整 CFD 主程序、FFT 和多重网格当时都不具备。如果按申报书从零补齐，两个月内很难做出可核验的结果。因此实际研究把主线收窄为：把五对角求解器做稳、把通信里多出来的结构零裁掉，并在真实多 GPU 上把对错和快慢说清楚；CFD 这一头，先用制造解 Poisson/Helmholtz 证明它能作为后续压力泊松或高阶线离散的底层模块。

工作大致分成四步。

第一步是把已有实现摸清，并补上能让后续实验站得住的工程基础。我们先核对了上游三对角代码和本项目五对角源码的边界，明确哪些是继承、哪些是扩展。随后修掉分布式通信里一处不安全的等待，补上非法尺寸、空分区、线程数和 communicator 不一致等输入检查，也把超过默认 32 位整数范围的工作区挡在分配和 kernel 启动之前。与此同时，用一组不依赖 Fortran 运行时的独立检查，把五对角缩约结构、28 槽打包和一般半带宽公式先在模型层对过。这一步结束时，求解器已经可以在干净的 NVHPC + MPI 环境里构建，并且有一条可复现的 28 槽正确性基线。

第二步是做通信裁剪。五对角按进程分区以后，每个进程两端要留下 4 个接口未知量；前向通信如果按“每条边界方程 7 个数、再去掉可本地重建的单位对角”来打包，一条线要传 28 个双精度数。继续看这 28 个数，里面还有 6 个位置在结构上恒为零。我们先在独立脚本里把 28 槽到 22 槽的固定映射逐项对过，再在 Fortran 里做成可切换路径：默认仍走 28 槽，需要时切到 22 槽。两边用同一套输入做数值对照，并补了动态内存检查和反复创建—求解—释放的生命周期测试。这一步只改打包和通信布局，没有顺手改消元公式，也没有把性能优化混进去。

第三步是把求解器放到真实多 GPU 环境里看，并补一个最小的应用闭环。环境方面，我们在每进程绑定一块 GPU 的节点上做了 1、2、4 GPU，以及双节点 8 GPU 的强、弱扩展，同时比较 host staging 和 CUDA-aware MPI，并保留 28/22 两种前向布局。应用方面，没有去重写整套流场软件，而是做了一个制造解 Poisson/Helmholtz 示例：在结构化网格上沿一个方向形成批量五对角线系统，调用本求解器，检查网格加密后的误差阶和残差。这一步的目的很明确，就是回答两件事：多卡时它到底对不对、快不快；它能不能接到后续 CFD/PPE 里用。

第四步是根据前面的计时结果做诊断，而不是继续堆功能。阶段拆分显示，通信和数据搬运占比不低，但通信与局部计算稳定重叠的收益不够确定，因此没有把 overlap 做成默认功能。锁页主机缓冲、按次 pinned 拷贝等改动也逐项做过对照，有的局部拷贝更快，端到端却没有稳定变好，最终没有并进主路径。目前仍在做研究版本的组合回归和冻结，论文还没有写成全文。也就是说，到结题材料整理时，算法与实验主线已经走完，软件收口和文字成果还在进行。

### 5.2 研究方法、关键技术

方法上，我们没有把“写出一套新程序”当成唯一目标，而是把推导、独立对照、源码实现和集群实验分成可以单独核验的环节。具体说，主要用了下面几类做法。

一是分层求解，而不是把整条五对角线集中到一个进程里做。每个进程先在本地做消元，只把两端接口方程留下；各进程的接口未知量再组成一个规模随进程数增长、但远小于原系统的缩约系统；求出接口值以后，再回到各进程做回代。这个框架来自上游三对角方法，五对角需要重新确认接口未知量个数、缩约系统带宽，以及哪些系数必须通信、哪些可以在本地重建。

二是按结构而不是按经验去裁通信。前向打包时，单位对角不传，结构上恒为零的槽位也不传；接收端按固定映射把 22 个数填回完整方程。这样裁剪不改变数学等价关系，只减少前向 payload。实现上保留 28 槽作为对照路径，避免一改布局就失去基线。

三是用独立真值约束 GPU 结果。缩约结构和槽位映射先用独立脚本做穷举或随机对照，Fortran 求解器再与之比较；应用算例则用制造解，既看残差，也看前向误差和网格收敛阶。数值上还专门看过弱对角占优、行尺度跨度很大、以及近奇异或零主元的情形，对不能安全继续的系统给出明确失败，而不是 silently 给出一个看起来很小的残差。

四是性能只认同输入、同精度下的重复计时。开发阶段的单卡多进程结果只用来调通程序，正式扩展性结论一律来自每进程独占 GPU 的作业。计时时区分局部计算、打包、MPI、缩约求解和回写，预热后再重复多次，报告中位数而不是单次最好值。外部对照方面，在单 GPU、固定规模的五对角问题上接入了 cuSPARSE 的 QR 路径，作为锚点而不是“全面优于现有库”的证明。

开发环境以 NVHPC 的 CUDA Fortran 和 MPI 为主，求解热循环在 GPU 上完成；独立数学检查可以在普通机器上先跑。系数和右端有一部分是原位覆盖的，因此调用方必须清楚数组在求解后不再保持进入时的内容。这些约束看起来琐碎，却决定了后续集成时会不会把别人的数据写坏。

## 六、结果分析

这一部分按实际完成的研究内容来写。有的结果和立项时的想象并不一致，尤其是多 GPU 扩展性，下面按证据说，不把预期写成已经达到。

### 6.1 五对角求解器本身：对得上，也知道自己不能干什么

先看正确性。独立检查、CPU/稠密对照和 CUDA Fortran 求解器可以对上：在已测的对角占优和制造解问题上，28 槽与 22 槽路径的差异保持在双精度舍入量级，剖面测试里最大均方根误差大约是 \(4.3\times10^{-16}\)，无穷范数大约是 \(6.7\times10^{-16}\)。输入防护也起到了预期作用：行数过小、系统数不合法、进程数多于系统数、线程数或通信域不一致，都会在进入求解前被拒绝；工作区或通信计数一旦超过当前 32 位整数合同，同样会在分配或启动 kernel 前失败，而不是在 GPU 上读到错误地址。

数值稳定性方面，结果比“残差很小就等于解对了”要完整一些。对预注册的弱占优、跨很多个数量级的行尺度，以及受控的近奇异系统，求解器给出了可重复的误差边界；真正遇到零主元或过小主元时，会以明确错误码停止。它目前没有主元交换，所以不能解释成已经能处理任意病态五对角系统。这一点对后面接 CFD 很重要：离散格式如果局部失去对角优势，不能指望线性求解器自动救回来。

和单 GPU 稀疏直接法比，在笔记本 GPU、双精度、固定规模 \(64\times64\times1024\) 的制造解问题上，本求解器中位时间大约 3.65 ms，同配置下 cuSPARSE QR 两次独立复测大约 5.6–6.7 ms。这个数字只说明：在这条 batched 带状问题上，专用求解器至少不是明显更慢。它不能外推到多 GPU，也不能说“已经全面超过现有库”。A100 上另有一次相近规模的并列计时，两者差距只有百分之三左右，同样只适合作为量级参考。

### 6.2 通信裁剪：结构上成立，时间上要看配置

28 槽减到 22 槽，数学上就是少传 6 个结构零。对五对角前向布局，这相当于 payload 元素数减少约 21.4%。独立映射检查覆盖了大批随机系统和故障注入，Fortran 可切换路径也与 28 槽在冻结容差内等价。所以，就“这种布局能不能无损编码”而言，结论是肯定的。

时间上则没有那么整齐。前向槽数变少，并不自动等于 MPI 总字节或端到端时间同比例下降，因为回传、局部消元、打包开销和启动开销都还在。单节点双 GPU、host staging、固定规模的一组正式对照里，22 槽相对于 28 槽的端到端变化中位数大约是加快 14.5%，而且差异主要出现在前向的设备—主机—MPI 这一段，局部计算几乎不变。但单进程时两者几乎没有差别；个别 device 路径上，22 槽甚至还略慢。因此比较稳妥的说法是：裁剪减少了前向要搬的数，在通信已经可见的配置里有机会换成时间，但它不是一张“换布局就全面加速”的牌。

这件事带来的启发很具体。带状求解器做到后来，真正还能动的往往不是再发明一种消元，而是把已经为零、已经可本地重建的量从通信里拿掉。与此同时，必须把“少传了几个数”和“墙钟时间变短”分开写，否则很容易把结构结果说成性能结果。

### 6.3 多 GPU 实验：程序能跑，但扩展性目前不好

真实多 GPU 实验是本项目里最不“好看”、却最有用的一部分。1、2、4、8 GPU 的强、弱扩展，以及 host/device、28/22 的配对都做了，双节点 8 GPU 正式结果里误差仍保持在 \(10^{-13}\) 量级，说明分布式路径在这些规模上是对的。

快慢则另一回事。从 1 GPU 强扩展到 8 GPU，加速比只有大约 0.39–0.46，效率大约 4.9%–5.7%；弱扩展效率大约 10%–13%。也就是说，进程和 GPU 加多以后，端到端并没有按计算量被分摊的比例变快，有的强扩展点甚至比单卡更慢。阶段计时也支持这个判断：MPI 及相关等待可以占到一半左右。我们据此评估过计算与通信重叠，预测中位数收益大约 11%，但预注册的稳定性门槛没有过，所以没有把 overlap 做成产品功能。锁页 staging 的按次拷贝可以让 D2H/H2D 快一截，端到端却出现过回退，相关候选后来也没有进入最终路径。

对结果的理解，我们现在比较明确。当前实现把很多独立线系统批在一起，单卡时 GPU 已经比较满；再切成多卡后，每卡分到的局部消元变少，接口缩约系统和 Alltoall 却随进程数变重。五对角每进程 4 个接口未知量，缩约系统规模是 \(4P\)，进程一多，通信和缩约求解就会很快变成主因。再加上实验环境并非总是 GPUDirect 那条理想路径，有的作业还走了强制 TCP，扩展性数字更不能说成硬件上限。

所以，这一部分能够成立的结论其实是两句：分布式五对角在真实多 GPU 上可以给出与单卡一致的解；就目前的实现和已测规模而言，它还不是一个已经展示出良好强、弱扩展的求解器。后一句不回避，反而决定了下一步不该去堆新功能，而该先盯通信路径、缩约求解和负载切分。

### 6.4 和应用的衔接：能证明“接得上”，还不是完整 CFD

申报书里的 FFT–GMG 和全流程流场软件，本轮没有做成。做成的是一个更小、但能说清楚的闭环：在四阶五点、Dirichlet 边界的制造解 Poisson/Helmholtz 问题上，沿一个方向拉出批量五对角线，交给本求解器。双 A100、双精度、32 组算例里，观测到的最低收敛阶大约是 3.99，最大缩放残差大约 \(4.4\times10^{-14}\)。这说明，至少在这条线求解路径上，离散、边界处理和线性求解是自洽的。

它不能代替方腔流、槽道流，也不能代替完整时间推进。制造解只验证“已知真值时这一段对不对”，不验证湍流模型、入口条件或整场守恒。我们把这一点写清楚，是为了让结题表述和源码一致：本项目交付的是可接入 CFD/PDE 软件的带状求解核心，以及它在 Poisson/Helmholtz 子问题上的证据；不是已经完成的工业级流场软件。

### 6.5 综合起来，现在能说什么、还不能说什么

把上面几块放到一起，实际研究给出的图景是：五对角分布式求解这条线已经从“能编译”走到了“有独立对照、有真实多 GPU 作业、有最小应用算例”；通信裁剪在结构上成立，性能收益则依配置而定；多 GPU 扩展性目前偏弱，这个负结果本身就是对后续工作最有用的约束。

还不能说的事情也同样清楚。论文全文尚未完成，公开范围和引用文本还待指导教师确认；研究版本仍在做组合回归和冻结，不能把进行中的候选写成已经发布的软件。一般半带宽 \(m\) 的接口规模和零槽计数已经做过独立复核，但它还不是生产级任意带宽求解器，也不适合写成“首次发现”或“通信量绝对下界”。至于申报书中的 FFT、多重网格和标准 CFD 算例，仍然是后续集成方向，不是本轮已经完成的模块。

对我们自己而言，最大的收获其实不是又多写了若干子程序，而是把判断标准从“程序跑通了”换成了“这句话能不能回到某次实验、某份日志和某一版源码”。有的优化看起来很合理，一对钟就站不住；有的裁剪在数学上很干净，时间上却只在通信已经暴露的时候才显现。这些地方如果在结题时仍写成全面成功，既不符合事实，也会把后面真正该做的通信和扩展性问题掩盖掉。
